# Retained AWS host: Linux prerequisites and capacity stop

Research date: 2026-11-25 America/Denver; commands ran on 2026-11-26 UTC.
This is a sanitized research record, not an M1 backend capability receipt.
Cloud account/resource identifiers and raw command records remain outside
the public repository.

## Scope and resource decision

The existing stopped x86_64 development instance was reused under the user's
AWS Free-plan authorization. Before starting it, the live account API reported
`FREE` / `ACTIVE` with remaining credits. The existing encrypted 40-GiB gp3
root volume and stop-on-shutdown behavior were checked. No new instance,
volume, paid upgrade, size change or permission change was requested.

The retained host ran Ubuntu 24.04, reported kernel `7.0.0-1017-aws` and had
two host vCPUs and approximately 8 GiB RAM. Its existing shared k3s service was
active; no pre-existing Burdettie service units were loaded at preflight.
Source checkouts, prior worktrees, Nix outputs, VM disks and logs were retained.

The preflight at `2026-11-26T01:04:01Z` measured **5,231,730,688 available disk
bytes**, against the existing **8,589,934,592-byte reserve**. This is below the
reserve before a new build starts. The current source/runtime build therefore
did not proceed. No dependency installation, source download, pruning or
infrastructure expansion was performed to force it to fit.

The host still supports useful compiler-free prerequisite tests. They used
disposable unprivileged processes and private sockets in tmpfs, without an
experiment checkout or dependency installation on the instance. Source and
results used the existing Systems Manager access path, which retains its
normal command records. No host security setting was changed. The small
command/result records were also retained in the existing CloudShell workspace.

Reproducer:
[`scripts/research/linux_host_preflight.py`](../../scripts/research/linux_host_preflight.py).
Run under the intended worker account with a bounded outer timeout:

```sh
timeout 90 python3 scripts/research/linux_host_preflight.py
```

On the retained host, the existing development account ran it through
`runuser`; the probe itself was **not root**. The remote command completed
with exit 0 and no stderr. This means the runner completed; individual outcomes
below carry the actual meaning.

The executed probe snapshot had SHA-256
`04708a9b2859e99951cbea1543156fbddc07c9754ffb63f8f07da909e6447689`.
After review, the checked-in reproducer gained explicit ctypes argument
declarations/native-width syscall values. It was not rerun on AWS after that
change. The recorded small-value x86_64 calls and remote outputs belong to the
executed snapshot, not an unobserved remote rerun.
The revised runner completed locally and reproduced that workspace's blocked
socket, memory and Landlock observations; this is not an AWS retest.

The Landlock child enabled `no_new_privs` before restricting itself. All
restriction/ptrace experiments were confined to disposable children; socket
paths were removed from their private tmpfs directory after the test.

The probe did not open the denied path before applying Landlock. Its observed
`EACCES` therefore lacks an unrestricted baseline and cannot by itself prove
that Landlock alone caused the denial. A future before/after test should verify
both paths' initial accessibility. The successful ruleset installation and
post-restriction outcomes remain valid scoped observations.

## The execution context matters

Before child-local restrictions, the development process had no effective
capabilities, `NoNewPrivs=0` and `Seccomp=0`. Its capability bounding set was
not empty. It inherited the SSM snap's AppArmor profile in **complain** mode.
The host reported unprivileged user namespaces enabled, the AppArmor
unprivileged-userns restriction setting enabled, and Yama `ptrace_scope=1`.

Those observations must travel with the results. Successful namespace
creation in this SSM-inherited context is not evidence that an arbitrary
desktop login or the proposed systemd worker service will have the same
authorization. No profile was disabled or changed to make the test pass.
Re-run capability and negative-policy checks under the actual declared worker
service before promoting any supported flag.

## Architecture consequence

The local restricted workspace's socket/memory failures do not establish that
Linux lacks the primitives needed by Darling. The real host supplied the
selected prerequisites. Conversely, these passes do not establish a complete
Darling runtime, a compatible Mach-O application or Burdettie enforcement.

The remaining immediate blocker on this retained host is capacity for the
selected current-source build under the existing reserve. Preserve the
upstream rootless control as the next runtime gate; do not respond to a
capacity limit by creating a new compatibility implementation or deleting
retained evidence. See [Darling research](2026-11-25-darling-runtime.md) and
[Linux enforcement research](2026-11-25-linux-enforcement.md).
